## 0. 今回確認した前提

以下を確認した。

- `company/policy.md`
- `company/ai-role.md`
- `company/ai/chatgpt.md`（自分のAI方針）
- `products/03-ai-meeting/input.md`

会社方針では、スタジオまあねの目的を「顧客にとって価値のある商品・サービスを作り、継続的な収益を生み出すこと」とし、面白さだけで商品化しないこと、推測と確認済み情報を区別することを求めている。Product 3 についても、この原則をそのまま適用する必要がある。

ChatGPT自身の役割は「総合分析・論理整理・商品企画・文章作成」であり、複数観点の整理、構造化、意思決定支援、文章化を得意領域としている。

Product 3 の input は、単なる「複数AI活用法」ではなく、「複数AIを組織として動かすために、共有された作業環境と共有された作業記憶をどう作るか」を中心テーマとしている。

# 1. この記事で一番伝えるべきこと

## 結論

**一番伝えるべきなのは「AIを複数使うこと」ではなく、「AIが前の仕事を読める共有作業記憶を作ることで、複数AIをチームとして扱える」という考え方。**

GitHubは主役ではない。

読者に残すべき一文は、例えば次のようなもの。

> AIを何個使うかより、AI同士が同じ情報を見て、前の仕事を引き継げる仕組みを作ることが重要だった。

その上で、スタジオまあねでは現在その実装としてGitHubを使っている、と説明する。

### なぜこの順番が重要か

「GitHubでAI会議をしています」から始めると、GitHubの使い方の記事に見えてしまう。

一方、

**複数AIを使う → 情報が分断される → 共通の作業記憶が必要になる → その実装としてGitHubを選んだ**

という順番なら、GitHub採用の理由まで自然につながる。

# 2. 現在の仕組みをどう説明するか

基本モデルは以下。

```text
                 オーナー
                    │
             input.md に課題設定
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
    ChatGPT       Claude       Gemini ...
       │            │            │
       └────── GitHub ───────────┘
                    │
             共通方針・input
             各AIのoutput
                    │
             後続AIが参照
                    ↓
             比較・反論・補強
                    ↓
                統合・原稿化
                    ↓
                 オーナー確認
```

ただし、この図を「自動システム」として描くのは危険。

現状は、AIが常時接続されたエージェントとして自律的に動いているわけではない。AIごとに作業を依頼し、GitHub上のファイルを介して情報を受け渡す方式である。

したがって、記事では **「非同期のAI会議」** という表現が最も実態に近い。

# 3. GitHubを共通作業場にした理由

## 本質的な理由

GitHubを選んだ理由は「AIと相性がいいから」だけでは弱い。

実際の理由は、今回の条件では次の組み合わせが大きい。

1. Markdown中心のテキストをそのまま扱いやすい
2. フォルダ構造を明確にできる
3. AIごとのoutputを分離できる
4. リポジトリ全体を一つの作業環境として管理できる
5. 変更履歴が残る
6. 人間が途中経過を確認しやすい
7. 無料で始められる
8. 将来的に自動化・GitHub Actions・API連携へ発展できる余地がある

GitHub Freeでは個人アカウントについて、公開・非公開リポジトリを無制限に作成でき、コラボレーターも無制限。非公開リポジトリでは無料プランの機能に制限があるが、今回のような小規模なMarkdown中心の運用では無料で始めやすい。

ただし、**「無料だからGitHub」だけにすると説明が弱い。** 無料のファイル共有サービスは他にもあるため、変更履歴・構造化・テキスト中心・将来の自動化まで含めた総合判断として説明するべき。

# 4. GitHubに至るまでの検討経緯

記事では、最初からGitHub一択だったように見せない方がよい。

### Google Drive

**長所**
- 多くの人に馴染みがある
- ファイル共有が簡単
- Google Docs等で共同編集しやすい
- 無料容量がある

**短所**
- AIごとのoutputやバージョンを構造的に管理するには工夫が必要
- 「会社の作業リポジトリ」というより「ファイル置き場」に近い
- Markdown中心の作業フローとの相性ではGitHubに一歩譲る

Google Driveは共有・編集権限を細かく設定できるため、単純な共同作業場としては十分有力。したがって、記事で「Google Driveではダメだった」と断言してはいけない。

### Notion

**長所**
- 非エンジニアにも分かりやすい
- データベース、ページ、リンクなど情報整理が強い
- チームのナレッジベースとして使いやすい
- 共同作業を前提にした設計

**短所**
- 今回のMarkdown＋フォルダ＋変更履歴中心の作業ではGitHubの方が自然
- AIごとのファイル成果物を大量に並べる用途では設計を考える必要がある
- 無料プランには複数メンバー利用時などの制限がある

Notionは「GitHubより劣る」のではなく、**目的が違う**と整理するべき。

### GitHub

**長所**
- リポジトリという単位で会社・productを管理できる
- Markdownを自然に扱える
- フォルダ構造が明確
- Gitによる変更履歴がある
- AIごとのoutputを分けやすい
- 将来的な自動化との接続先として発展性がある
- 現在のスタジオまあねの作業方式に合った

**短所**
- 一般ユーザーには難しく感じられる
- 本来はソフトウェア開発向けのサービス
- AIによって読み書き能力や接続方法が異なる
- GitHubを採用しただけではAI同士は自動で会話しない

### 判断

> 「一番優れたサービスを選んだ」のではなく、「現在のスタジオまあねの条件では、GitHubが一番扱いやすかった」。

この表現が適切。

# 5. 各AIが共通方針を参照する仕組み

現在の構造は明快。

```text
company/
├─ policy.md       ← 会社として守るルール
├─ ai-role.md       ← 全AI共通の役割・作業ルール
└─ ai/
   ├─ chatgpt.md    ← ChatGPT固有の役割
   ├─ claude.md
   ├─ gemini.md
   ├─ grok.md
   ├─ qwen.md
   ├─ kimi.md
   └─ musespark.md
```

この構造の面白さは、**「共通ルール」と「個別能力」を分離していること。**

例えば、会社としては全AIに「顧客価値・収益性を優先する」という共通ルールを持たせる。一方で、ChatGPTには総合分析・論理整理、別のAIには別の得意領域を担当させる。

つまり、

> 全員が同じ会社の方針で動くが、全員を同じAIにはしない。

という設計。

### 重要な注意点

ここは誤解されやすい。

**ファイルを置いただけではAIが自動的に会社方針を守るわけではない。**

`ai-role.md` 自体が「読むこと」を共通ルールとして指定しており、各AIへの実行プロンプトなどでその読み込みを促す必要がある。

したがって、記事では「GitHubに会社方針を置けばAIが勝手に共有認識を持つ」と書いてはいけない。

正確には、

> AIに毎回参照させるための「外部化された会社の記憶・ルール」をGitHubに置いている。

と説明する。

# 6. 各AIがお互いのoutputを参照する仕組み

Productごとに、例えば以下の構造。

```text
products/
└─ 03-ai-meeting/
   ├─ input.md
   ├─ output/
   │  ├─ chatgpt/
   │  ├─ claude/
   │  ├─ gemini/
   │  ├─ grok/
   │  ├─ musespark/
   │  ├─ qwen/
   │  └─ kimi/
   └─ final/
```

重要なのはフォルダそのものではなく、**成果物を「共有された外部記憶」として扱うこと。**

例えば、

- ChatGPTが初期分析
- ClaudeがChatGPTの分析を読む
- Geminiが両者を読む
- 別のAIが反論する
- 統合AIが全成果を比較する

という流れを作れる。

これなら「7つのAIに同じ質問をして7つの答えを集めただけ」とは違う。

ただし、ここでも注意が必要。

**Product 3の現時点では、まだこのproduct自身のoutputは存在しない。** また、Product 2では各AIのoutputフォルダに実際の成果物が存在することは確認できるが、リポジトリだけから「7AIが必ずこの順番で互いのoutputを読み、反論し合った」とまでは証明できない。

したがって、記事では「設計としてこうする」「今回実際にこういう順番で実行した」とを分ける必要がある。

これは今回の記事の信頼性に直結する重要ポイント。

# 7. 「AI会議」と呼べるポイント

## 呼んでよい理由

人間の会議の本質を「同じ議題について、複数の参加者が意見を出し、他者の意見を踏まえて議論し、結論を作ること」と考えるなら、今回の方式には会議的な要素がある。

- 同じ議題がある
- 複数の参加者がいる
- 参加者ごとに異なる観点がある
- 他者の成果物を読む
- 反論・補強・修正ができる
- 最終的に一つの成果物へ統合する

## ただし「普通の会議」ではない

正確な呼び方は、

> **GitHubを介した非同期AI会議**

または

> **共有ファイルを使ったAI間の非同期レビュー／討議**

がよい。

「AIが会議室でリアルタイムに話し合っている」というイメージは避ける。

また、「マルチエージェントシステム」と断言するのも慎重にする。一般的なマルチエージェントシステムは、複数のAIエージェントがプログラム上で相互作用し、自律的にタスクを進める構成を指す場合が多い。スタジオまあねの現在の方式は、そこまで自動化されていない。

# 8. 現在の仕組みの限界

ここは記事の重要な見せ場にするべき。

### 限界1：人間が「司会者」になっている

現在はAI同士が完全自律的に次のAIを呼ぶわけではない。

人間がテーマを設定し、各AIに作業を依頼し、必要に応じてファイルを更新する。

つまり、現状の正確な表現は「AIだけの会社」ではなく、**人間1人＋AIチーム**。

### 限界2：GitHubは共有場所であって、議論エンジンではない

GitHubにファイルを置くだけでは議論は起きない。

「誰が」「いつ」「どのoutputを読んで」「何を反論するか」という運用設計が必要。

### 限界3：AIが他AIの誤りを増幅する可能性

前のAIのoutputを次のAIが読むと、情報共有というメリットがある一方、誤情報も引き継ぐ。

そのため、後続AIには「前のAIを信じる」のではなく、「前のAIをレビューする」役割を与える必要がある。

### 限界4：情報量が増えるほど管理が難しくなる

AIが7つなら7つ分のoutputが生まれる。

productが増えるとファイル数も増える。

「全部読ませる」方式は、いずれコンテキスト量・時間・整理コストの問題にぶつかる。

### 限界5：AIごとのGitHub能力が違う

GitHubを読めるAIと、書き込めるAIは同じではない。

このため「7AIが全員GitHub上で自由に働いている」という表現は不正確。

### 限界6：GitHub自体が読者の壁になる

非エンジニアにはGitHubのフォルダ構造やMarkdownが難しく見える可能性がある。

記事ではGitHubの使い方を詳しく教えるより、「なぜ共有作業場が必要なのか」を中心にし、GitHubは具体例として説明する方がよい。

# 9. 読者が一番面白いと思いそうなポイント

優先順位は以下。

## 1位：「AIを7人雇ったら会社っぽくなるのか？」

これはスタジオまあねの物語として強い。

ただし、AI社員という比喩だけで終わると薄い。

「社員を増やす」→「でも社員同士が互いの仕事を知らない」→「そこで会社の共有フォルダを作った」という流れにすると、読者が仕組みを理解しやすい。

## 2位：「AI同士はどうやって会議しているの？」の種明かし

読者が期待する「実はこうでした」を作れる。

答えは、

> 会議室はありません。GitHubにファイルを置いています。

という少し笑える構造。

## 3位：「7AIに同じ質問するだけ」と何が違うのか

ここは記事の実用価値が高い。

```text
従来
同じ質問 → 7AI → 7回答 → 人間が読む

スタジオまあね方式
課題 → AI A → output
           ↓
         AI Bが読む
           ↓
         AI Cが読む
           ↓
       比較・反論・補強
           ↓
         統合成果物
```

この違いを図解すると強い。

## 4位：「本当に会議なの？」というツッコミ

先回りして自分たちでツッコむ。

「いや、リアルタイムで喋ってないので、会議というより交換日記に近いです。」

のようなユーモアは、仕組みを正確に説明しながら読者を引き込める。

# 10. 記事全体の構成案

- Product 2からの自然な導入

- しかし個別に質問するだけでは情報が分断される

- Notion
- GitHub
- 比較軸
- 最終的にGitHubを採用
- 「GitHubが最強」ではなく「今の条件で一番扱いやすかった」

## 第4章　GitHubに会社を作ってみた

- `company/policy.md`
- `company/ai-role.md`
- `company/ai/*.md`
- AIごとの役割
- 共通ルールと個別能力の分離

## 第5章　AIたちの会議室は「output」フォルダだった

- `input.md`
- AIごとのoutput
- 後続AIが前の成果を読む
- 反論・補強・修正

※ここは、実際の履歴・プロンプト・outputを確認してから書く。確認できない部分は創作しない。

## 第7章　でも、これは本当に「会議」なのか

- リアルタイムではない
- 完全自動ではない
- 人間が進行している
- AIは前のAIを無条件に信用してはいけない
- 「非同期AI会議」という位置づけ

## 第8章　やってみて分かったこと

### メリット
- 共通記憶
- 役割分担
- 比較・批判
- 履歴
- 再利用

### デメリット
- ファイル管理
- AIごとの接続差
- 人間の手間
- 情報の増殖
- 誤情報の連鎖

## 第9章　自分で作るなら、AIは3人で十分

最小構成を提示。

1. AIを3つ選ぶ
2. 共通方針を1ファイルにする
3. 共通作業場を作る
4. input/outputを分ける
5. AIごとの役割を決める
6. 前の成果を次のAIに読ませる
7. 最後は人間が判断する

「最初から7AIにする必要はない」と明確にする。

## 第10章　スタジオまあねは、この先どうするのか

- 現状は実験段階
- GitHubを将来も使うとは限らない
- 自動化できる部分はまだ多い
- 次のproductで何を試すかを予告
- 「AIチームを作ったら、本当に月1万円を生み出せるのか」という本来の経営目的へ戻す

# 12. 企画上の重要な指摘

## 指摘1：GitHubを説明しすぎると、記事のテーマがズレる

この記事はGitHub入門ではない。

**テーマは「AI同士をチームとして働かせる方法」。GitHubはその実装例。**

GitHubの画面やGit操作の説明は最小限にする。

## 指摘2：「AI会議」という言葉は強いが、説明不足だと誇大広告になる

タイトル・導入で「AI会議」と言い切るのは面白い。

しかし本文の早い段階で、

> 実際にはリアルタイム会議ではありません。
> GitHub上のファイルを介した非同期のやり取りです。

と明かすべき。

この「期待→種明かし」がむしろ記事の面白さになる。

## 指摘3：「共通方針を参照する」だけでは、会社としての一貫性は保証されない

ファイルはルールを保存する場所であって、ルールを強制する仕組みではない。

この点を明示すると、記事の技術的な信頼性が上がる。

## 指摘4：Product 2の実例は「実際に何が起きたか」を確認してから使う

Product 2には実際のoutputファイルが存在する。しかし、リポジトリの構造だけからAI同士の具体的な会話順序を推測してはいけない。

記事で「ClaudeがChatGPTに反論した」などと書く場合は、実際のプロンプト・output・作業履歴を根拠にする。

## 指摘5：最大の読者価値は「GitHubの使い方」ではなく「共有記憶という考え方」

GitHubを使わない読者にも、

> 共通ルール＋共有された成果物＋役割分担＋レビュー

という考え方を持ち帰ってもらう。

これができれば、将来Notionなどに移行しても記事の価値が残る。

# 13. 最終的な企画メッセージ

記事全体の中心メッセージは、次の3段階にするとよい。

「AIを7人使っています。」

「でも、7人に別々に質問しているだけではチームにならなかった。だから共通の作業場と共有記憶を作った。」

### 本質
「複数AIを組織として使う鍵は、AIの数ではなく、AI同士が仕事を引き継げる仕組みを作ること。」

> そこを試している。

# 15. 最新仕様に関する調査メモ（2026-08-16時点）

- GitHub Freeは個人アカウントで公開・非公開リポジトリを無制限に利用でき、コラボレーターも無制限。非公開リポジトリでは無料プランの機能制限がある。
- GitHubはpull request等によるレビュー・変更履歴を備えており、「成果物を残して後から確認する」という今回の用途と親和性がある。
- Google Driveはファイル・フォルダ共有と閲覧／コメント／編集権限を提供している。単純な共有作業場として十分な選択肢である。
- GoogleアカウントにはDrive等で共有される無料ストレージが最大15GBある。
- Notionは共同作業を前提とした共有・権限管理を備え、無料プランもある。ただし複数メンバー利用時などに制限があるため、今回の用途では実際の運用条件を比較して判断する必要がある。

## 判定

**企画としては成立性が高い。**

ただし、この記事の価値を決めるのは「GitHubを使っていること」ではない。

**実際のAIのoutputを材料にして、「どのAIが何を読み、どう意見が変わったか」を見せられるかどうかが最大の勝負。**

そこを確認できないまま「AI会議」を完成原稿にすると、単なる仕組み紹介になり、スタジオまあねの公開実験としての面白さが弱くなる。

したがって、次工程では実際のProduct 1・2の履歴とoutputを証拠として掘り起こすことを優先する。
